Análise de performance de algoritmos de ordenação aplicada aos focos de incêndio em São Paulo

Um sistema que lê os focos de incêndio detectados por satélite no estado de São Paulo em 2023 e 2024, ordena esses dados com seis algoritmos implementados pelo grupo e mede, a cada ordenação, quantas operações cada algoritmo precisou fazer.

Objetivo

Desenvolver um programa capaz de organizar e ordenar a base de focos de incêndio do INPE por data, bioma e município, informando a cada solicitação o número de operações (comparações e trocas) realizadas.

Para isso, o grupo implementou à mão seis algoritmos clássicos de ordenação — sem usar os métodos prontos da linguagem — e construiu este painel para executar, medir e comparar cada um deles sobre os mesmos dados reais.

Por que isso importa

Incêndios em regiões críticas comprometem a biodiversidade e alteram o clima. O monitoramento por satélite gera grandes volumes de dados geográficos, e analisá-los rapidamente é o que permite fiscalizar e agir a tempo.

A ordenação é a etapa inicial do processamento: dados organizados são o ponto de partida para técnicas de aprendizado de máquina e deep learning que classificam áreas atingidas ou preveem padrões de queimadas. Escolher o algoritmo certo faz diferença quando os dados crescem.

Os dados

Os arquivos vêm do Programa Queimadas do INPE (Instituto Nacional de Pesquisas Espaciais), na série do satélite de referência, que usa sempre o mesmo satélite para permitir comparar anos diferentes. O grupo trabalhou com o estado de São Paulo, anos de 2023 e 2024, em formato CSV.

Como o sistema funciona

  1. CSV do INPE2 arquivos, um por ano
  2. LeituraLeitorCsv converte cada linha e descarta as quebradas
  3. Ordenação6 algoritmos + Metricas contando as operações
  4. Serviçoscopiam os dados, medem o tempo, calculam estatísticas
  5. API RESTJavalin responde em JSON
  6. Painelnavegador: tabelas, gráficos e mapa

O back-end é escrito em Java 21 e organizado em camadas: cada uma tem uma única responsabilidade (ler, ordenar, coordenar, responder). O painel é feito em HTML, CSS e JavaScript, com Chart.js para os gráficos e Leaflet para o mapa, e não faz nenhuma ordenação por conta própria: tudo o que ele mostra vem da API.

Como o desempenho é medido

Comparações
Quantas vezes o algoritmo perguntou "este elemento vem antes daquele?". O comparador do critério é "embrulhado" por outro que soma 1 a cada chamada (padrão de projeto Decorator), então nenhuma comparação escapa da contagem.
Trocas / movimentações
Quantas vezes um elemento mudou de posição: cada troca de dois elementos (Bubble, Selection, Quick, Heap), cada deslocamento (Insertion) ou cada cópia de volta para a lista (Merge, que não troca).
Tempo
Medido com System.nanoTime() só durante a ordenação. Varia com o computador e a carga do momento; por isso as contagens de operações são a medida principal de comparação.
Mesma entrada
Cada ordenação trabalha sobre uma cópia dos dados originais. Assim, um algoritmo nunca recebe a lista já ordenada pelo anterior, e as medições são justas.
